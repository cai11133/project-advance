# 发布与部署

用户要求发布、部署，或项目收口发现需要部署时，读取对应章节。发布和部署分别确认、分别验证。

## 发布版本

1. 核对目标仓库、版本号、待发布提交和预定发布范围。有 Milestone 时核对其 Issues、关联 PR 与验收证据。必要项未验收时，列出差项并暂停发布。
2. 按仓库约定准备发布说明和版本改动。若需要先合并 `CHANGELOG.md` 等改动，按开发流程完成后重新核对待发布提交。展示版本号、最终提交、发布范围和 GitHub 操作，取得发布授权。
3. 核对同名 tag 和 Release 的现状。已有同名 tag 时，解析其指向的提交并与已确认提交比对，存在冲突时停下，不覆盖。缺 tag 时按授权为指定提交创建并推送。核对远程 tag 后，按授权创建 Release 或发布关联的既有草稿，已有一致的正式 Release 可复用。使用 `gh release create` 时加 `--verify-tag`。
4. 重新读取远程 tag、Release 和提交，确认 Release 已发布。汇报版本、提交、Release 链接和验证结果。部分步骤成功或请求超时时，以实际远程状态决定是否接续。

## 部署

### 版本来源

正式部署前核对远程 tag 指向的完整提交 SHA，并确认已发布的 GitHub Release 关联同一个 tag。缺少 tag 或 Release 尚未发布时，先说明还需发版，取得发布授权后走发布流程。紧急修复使用补丁版本，发版与部署分别确认。

### 工作环境与部署目标

沿用已有项目的部署说明和实际环境。项目没有部署约定且用户未指定环境时，默认方案面向用户自己的本机，服务管理方式按其操作系统选择。

- 云端会话遇到本机部署时，默认先出方案，请用户在本机会话继续。项目已有明确授权且实测可用的远程部署通道时，按获批方案执行。部署前核对实际操作的机器和目标环境。
- 新项目部署到本机时，把开发、正式运行和数据放在独立目录，用系统自带的服务管理器管理进程，默认监听 `127.0.0.1`：macOS 用 `launchd`，Linux 用 `systemd` 用户服务，Windows 用任务计划程序或 Windows 服务。需要从其他设备访问时，将 Tailscale 或项目约定的访问方式和范围列入方案。
- 新项目有持久数据时，可从每天备份、保留最近 14 份开始。备份位置、保留和恢复方案一并审核。

### 用户审核与执行

1. 核对目标环境、发布版本、实际运行版本和健康检查，明确涉及的服务、配置和数据。
2. 向用户说明部署原因和预期影响，提交目标环境、版本及提交 SHA、步骤、验证、备份和回滚方案供审核。涉及数据库迁移时，确认旧版能否使用迁移后的数据，以及何时需要恢复数据。涉及 `.env`、plist 等配置时，方案只记录位置、变量名和变更范围，恢复所需密钥按项目约定单独受控保管。文档、Git 和日志只用占位符呈现密钥。补齐关键缺口并取得对本次方案的明确批准后执行。
3. 涉及数据库或其他持久数据变更时，先生成一致性备份，在隔离位置做恢复校验，再变更目标环境。运行中的 SQLite 用 `.backup` 或备份 API 生成快照，恢复后核对数据库完整性和关键数据。已有项目的停写备份按其经验证的流程执行。部署失败时，先核实实际运行版本、服务和数据状态，再按获批方案处理，覆盖式恢复须单独确认。
4. 从实际运行环境核对版本和健康检查，必要时实测本次变更涉及的关键页面或接口。汇报目标环境、实际运行版本与提交、健康检查、备份和恢复校验结果（如涉及）及未验证项。恢复旧版时同样核实实际运行版本和服务状态。

### 涉及数据库迁移的部署审批模板

部署前填写下表。预先写明验收标准，执行后逐项补上结果和证据。

| 审批项 | 待填内容 |
| --- | --- |
| 部署与迁移范围 | [目标环境、当前和目标版本及提交、数据库与表、迁移步骤、预计停写时间和业务影响] |
| 备份与恢复校验 | [一致性备份的时间与位置、恢复校验环境、数据库完整性与关键数据核对结果、证据] |
| 旧版与迁移后数据库的兼容性 | [分别填写读取与写入：通过／失败／未验证；列出旧版实际使用的关键操作、结果和证据。只测读取时，写入填未验证。] |
| 回滚路径与停点 | [何时停止部署或回滚；只回滚程序需要哪些兼容性证据；何时还需恢复数据库；所需批准及操作顺序] |
| 恢复旧快照的影响 | [从备份时间到停写之间新增、修改或删除的数据；如何在恢复前保存当前库；哪些变更要重放、补录或由用户确认放弃；差异未知时写明核对方法] |
| 部署或恢复后的验收 | [运行版本及提交、数据库完整性与必要的约束检查、关键记录、关键业务操作；逐项填写预期、通过／失败／未验证及证据] |

只回滚程序前，确认旧版能执行该阶段需要的数据库操作。必要操作失败或未验证时，暂停切换，补齐证据或调整方案。需要恢复旧快照时，先核对备份后的写入并保留当前库；按获批方案处理这些变更，覆盖式恢复仍须单独确认。

#### SQLite 回滚审批填写示例

以下结果来自 macOS 上 SQLite 3.54.0 的隔离演练，使用合成证照数据。实际项目按旧版需要执行的业务操作重新验证。

| 迁移方式 | 兼容性与验收证据 | 回滚路径与停点 |
| --- | --- | --- |
| 新增可空列 | 旧版新增返回 HTTP 201，修改返回 HTTP 200。重复主键返回 HTTP 409，同一事务中先前的修改已回滚。新版读回返回 HTTP 200，确认新增和修改已成功保存，原有记录的新字段值仍保留。 | 对本次已验证的操作，可以只回滚程序，保留迁移后的数据库和已写入的数据。若旧版还需要执行其他写入，先验证再恢复对应业务。 |
| 重命名旧版依赖的列 | 旧版新增和修改均返回 HTTP 503。新版读回返回 HTTP 200，确认两次失败请求均未改动数据。 | 保持停写，保存迁移后的数据库，核对备份后产生的变更并提交恢复方案。用旧快照覆盖当前数据库前按要求单独确认。 |

两种迁移的 SQLite 完整性检查均通过，外键检查均未发现违规。
