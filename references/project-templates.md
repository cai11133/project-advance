# 项目文件与模板

## 文件标准

新建项目按用途选模板。接入旧项目先找实际文件、分支、未提交改动和现有任务，沿用已有位置，只提影响接续的缺项。

| 位置 | 何时使用及内容 |
| --- | --- |
| `README.md` | 新建独立项目时，说明用途、开始方法和文档入口。 |
| `AGENTS.md` | 有长期 AI 工作规则时，写边界、验证、记录位置和收口。 |
| `tasks/<任务短名>.md` 或 GitHub Issue | 一项可独立验收的任务只维护一份主记录。 |
| `CONTEXT.md` | 需要统一业务术语或规则时使用；已有 `GLOSSARY.md` 或工具配置指向同类文件时，使用一份权威记录。 |
| `ROADMAP.md` 或 GitHub Milestone | 多阶段项目用 ROADMAP 导航；GitHub 路径以 Milestone 维护版本目标与进度，由任务主记录维护单项进度。 |
| `docs/adr/NNNN-<短标题>.md` | 记录难以逆转且需要追溯的关键取舍。 |
| `docs/discovery.md`、`docs/prd.md`、`docs/archive/` | 有独立调研、规格或归档需要时按项目约定使用，并从任务单引用相关材料。 |
| `SKILL.md`、`references/` | 交付物本身是 Skill 时使用。 |
| `.gitignore`、`.env.example` | Git 项目有本地配置或生成物时按需维护。示例配置用占位符。 |
| `LICENSE`、`CHANGELOG.md` | 按项目的许可或版本记录需求维护。 |
| `.github/ISSUE_TEMPLATE/`、`.github/pull_request_template.md` | GitHub 协作需要固定表单时启用，沿用任务和验收字段。 |
| `.github/workflows/`、`.devcontainer/devcontainer.json`、部署和备份脚本 | 需要相关环境时，按项目约定维护。 |

## 任务单

本地文件和 GitHub Issue 用同一结构。已知资料直接使用。先明确会影响开工的关键缺口，确认后选择可跑通的最小流程。状态按实际采用待确认、进行中、待审、已合并、已完成或已转接。已有记录缺历史证据时写「未找到记录」。

```markdown
# <任务短名>
状态：待确认
主记录：<本地任务单路径或 Issue 链接>

## 背景
<谁遇到什么问题，现有情况>

## 范围
- 范围内：<本次覆盖>
- 暂缓：<已知暂缓事项>

## 目标
<完成后可观察到什么变化>

## 产物
<文件、入口、链接或其他交付物>

## 验收标准
- [ ] <实际入口、条件和预期结果>

## Checklist
- [ ] <一项执行动作>

## 验收历史
- <日期>｜<验收项>｜<通过、失败或未验证>｜<证据或原因>｜<适用时的提交>

## 交接
- 已完成：<实际完成及未提交工作位置>
- 验证结果：<结论和证据>
- 卡点：<当前阻塞>
- 下次第一步：<可立即接续的动作>
```

执行 Checklist 随实际动作更新。验收标准有证据通过才勾选，失败或未验证保留原结果，复验追加日期、结果和证据。暂停或收口时先同步本次变更、清单和证据，再更新四行交接。未获 GitHub 写入授权时给出草稿。

## 从本地转接 GitHub

1. 一次呈现目标仓库、Issue 草稿、可共享证据和切换动作，取得明确授权。审批前在对话中给草稿。只能本地访问的证据记录结果和访问范围。
2. 首次创建前，在本地任务单保存一个无敏感信息的唯一转接标识。将同一标识写入 Issue 正文（例如 Markdown 注释）。复用该标识，用已知链接或在目标仓库读回正文查找匹配项。找到唯一匹配时接续该 Issue；存在多个匹配或无法核实创建结果时，暂停再次创建并报告。
3. 创建后从 GitHub 重新读取正文，核对标识、开工六项、Checklist、验收历史、可共享证据和下次第一步。通过后在原本地任务单页首写 `主记录：<Issue URL>`、`状态：已转接`，读回确认回链。两个核对都成功才完成切换。核对未完成时，本地仍是主记录。
4. 后续从 Issue 记录变化。标记已转接的本地文件保存历史，「继续」时沿页首链接定位 Issue。Issue 暂时不可访问时保留切换状态并说明卡点。

## 规划工具

按本次需求核对已安装工具和项目已有配置。整理规格可用 `to-spec`，拆独立验收子任务可用 `to-tickets`，按规格实施可用 `implement`，名称以实际工具为准。给工具同一份任务和适用的术语表，按项目主记录归档规格、子任务链接及验收证据。子任务沿用项目现有的任务目录或跟踪器；新建本地项目默认沿用 `tasks/`。工具的默认位置与项目约定不一致时，先出草稿，把实际写入位置列入本批计划。确认它计划使用的命令、写入位置和标签；实际创建对象、打标签或提交遵守本批许可。工具不可用时，按项目流程继续整理草稿。

## AGENTS.md

采用以下六条基线，填写本项目验证方法和记录位置。旧项目沿用已有规则，提出必要补丁。项目规则可增加限制；遇到授权或暂停规则冲突，先暂停相关操作并解释。

```markdown
# AGENTS.md

## 一直遵守的规则
- 先读仓库规则和相关文档、Issue 或交接记录。沿用已有做法，保护现有文件和未提交改动。
- 目标、范围或验收有歧义时，列出理解和影响，一次问一个关键问题。普通细节沿用项目惯例，说明影响结果的假设。
- 多步骤任务或预计改动 3 个及以上文件时，先列计划、文件和每步验证方式，等待确认。每完成一步，简报改动和验证结果。
- 要改计划外文件、偏离已确认计划、前提不符、同一验证连续失败三次或涉及不可逆操作时，暂停并说明进展和选项。
- 只做任务所需改动，先检查已有实现并复用。保护敏感凭据，汇报用脱敏信息。
- 按明确授权执行提交、推送、GitHub 写入、合并、发布和部署。本次对话中已明确授权的同一操作按原范围接续。

## 本项目执行要求
- 工作边界：<真实约定>
- 验证方法：<实际命令或入口及通过判据>
- 记录位置：<主记录、证据和规则的实际位置>
- 暂停与收口：<需要同步的项目内容>
```
